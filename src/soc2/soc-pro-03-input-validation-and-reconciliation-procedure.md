## 1. Purpose

This procedure puts SOC-POL-01 statements 4.3 to 4.6 into daily practice. It defines the catalogue of inputs, the validation rules each input must pass, what happens to an input that fails, and the daily reconciliation that proves nothing was lost, duplicated or changed between receipt and processing.

## 2. Scope

All inputs to services whose processing integrity category is in the report scope: files, interface calls, messages, user forms, manual entries by staff and data fed from other systems. It covers the point of receipt through to confirmation that processing consumed the input.

## 3. Roles and responsibilities

| Role | Responsibility |
|---|---|
| System Owner | Keeps the input catalogue and validation rules, approves changes to them, reviews monthly measures. |
| Operations team | Monitors validation results, works the quarantine, prepares and reviews reconciliations. |
| Developer | Implements validation and reconciliation checks as specified, with automated tests. |
| Submitter (customer or internal team) | Supplies inputs in the agreed format and corrects rejected items. |
| Information Security Manager | Tests the controls under SOC-PRO-01. |

## 4. Procedure

4.1 **Input catalogue.** The System Owner keeps, within the processing specification, a catalogue of every input: name, source, channel, format, expected volume and timing, authorisation method, owner, and the validation rules that apply. A new input is added to the catalogue before it goes live and the entry is reviewed at each change under GOV-PRO-09.

4.2 **Validation rules.** For each input the System Owner defines rules in the following classes and writes the specific values in the catalogue.

- Format: type, length, encoding, schema version.
- Range and domain: permitted values, minimum and maximum, dates that cannot be in the future.
- Referential: identifiers must exist in the master data they refer to.
- Completeness: mandatory fields present; for a batch, header and trailer present and record count equal to the trailer count.
- Duplication: an item with the same key as one already accepted inside the deduplication window is rejected or flagged, as the specification states.
- Authorisation: the submitter is authenticated and permitted to send this input for this account.

4.3 **Implementation and testing.** The developer implements each rule with an automated test that proves a failing item is rejected and a passing item is accepted. Rules are deployed through GOV-PRO-09 and the change record references the catalogue version.

4.4 **Control totals.** Every batch input carries a record count and, where values are numeric, a control total generated by the sender. The system compares the received count and total to the batch header before processing. A mismatch rejects the whole batch.

4.5 **Rejection and quarantine.** A rejected item or batch is written to a quarantine store with the reason code, the time, the submitter and the item identifier. Nothing is deleted and nothing is corrected automatically unless the specification names the correction (trimming surrounding spaces, for example) and the correction is logged. The submitter is notified within [Number] hours with the reason.

4.6 **Working the quarantine.** The operations team reviews the quarantine at least daily. Each item is dispositioned as Resubmitted (corrected by the submitter and accepted), Corrected internally (only on the submitter's written instruction, recorded against the item, entered by one person and verified by another), or Closed without processing (with the submitter's agreement). An item in quarantine for more than [Number] working days is escalated to the System Owner.

4.7 **Daily reconciliation.** At the end of each processing day the operations team reconciles, for each input: items received, items accepted, items rejected, items processed and items pending, so that received equals accepted plus rejected, and accepted equals processed plus pending. The figures come from system counts, never from manual tallies.

4.8 **Differences.** Any difference, or any pending count older than the specification's tolerance, is investigated the same working day. The investigation records the cause, the items involved, the correction and who verified it. A difference caused by a defect raises a change under GOV-PRO-09 and, where a customer commitment was affected, an incident under GOV-PRO-07.

4.9 **Reconciliation record.** The reconciliation is recorded with date, service, the five figures, differences and their disposition, preparer and reviewer. The reviewer is not the preparer. The record is retained for the examination period plus one further period.

4.10 **Interface reconciliation.** For inputs received from another system by interface, the sending system's daily count is obtained and compared to items received at least daily. Each interface is listed in GOV-REG-25 with its reconciliation method.

4.11 **Monitoring.** The System Owner reviews monthly: rejection rate by reason, quarantine ageing, reconciliation differences and time to resolve, and rule changes. A rising rejection rate for one submitter is raised with that submitter; a rising rate across submitters triggers a review of the rules.

## 5. Records and evidence

- The input catalogue inside each processing specification, version controlled.
- Automated test results for validation rules, retained with the release.
- Quarantine store entries and submitter notifications.
- Daily reconciliation records with preparer and reviewer.
- Difference investigations and the changes or incidents they raised.
- The monthly monitoring report.

## 6. Exceptions

A reconciliation may be performed weekly instead of daily only for an input with fewer than [Number] items per week, recorded in the catalogue and approved by the Head of Engineering. No exception permits silent correction or deletion of a rejected item.

## 7. Review and maintenance

The Head of Engineering reviews this procedure annually, after any processing incident, and when an input is added or changed. Changes follow GOV-PRO-01.
